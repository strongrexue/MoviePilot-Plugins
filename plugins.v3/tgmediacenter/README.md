# 胖虎媒体中心

MoviePilot V3 插件，聚合以下能力：

1. **TG 核心凭证**：Telethon 个人账号登录（StringSession）、对话列表缓存、转发冷却与保活。
2. **115 网盘**：扫码登录、空间配额、分享链接转存、磁力 / eD2k 离线下载（自实现 Web 接口，无额外依赖）。
3. **TG 资源监控**：实时监听 TG 频道，消息净化后由宿主识别引擎解析，按规则决策并推送（仅缺失 / 仅推已订阅 / 关键词过滤）。
4. **历史消息缓存**：回抓频道历史消息建本地索引，新增订阅时自动回搜并推送缺失资源。
5. **TG 通用转发**：关键词 + 文件扩展名两级匹配，支持内容转换与转发后置顶。
6. **运行详情与仪表盘**：插件详情页展示 TG / 115 / 缓存状态卡、最近流水与快捷操作；首页仪表盘卡片给一眼概览。

> 自定义豆瓣源（原 P3）已取消：豆瓣 RSS 订阅请使用「豆瓣中心」插件。

## 依赖与复用

- 额外依赖仅 `telethon`；RSS、识别、媒体库查询、通知、代理均复用宿主能力。
- 自有数据表通过 `plugin_declarative_base()` + `get_database_models()` 由宿主建表。

## 界面

Vue 联邦远程组件，暴露 `./Config`、`./Page`、`./Dashboard` 三个入口。

## 已知行为（排查时先看这里）

### 更新插件后前端没变化 / 仍报旧错误

联邦入口固定叫 `remoteEntry.js`（无哈希），宿主加载器也不追加缓存参数，而 SPA 只在
**页面加载时**拉取一次远程组件。因此**更新带前端改动的版本后，必须整页硬刷新
（`Ctrl + Shift + R`）**，否则浏览器仍在使用旧组件代码。

排查顺序：

0. **先确认插件是否真的更新到目标版本**（容器内直接读落盘文件）：
   ```bash
   docker exec <容器名> sh -c \
     "grep -o 'plugin_version = \"[^\"]*\"' /app/app/plugins/tgmediacenter/__init__.py; \
      grep -o \"FRONTEND_VERSION = '[^']*'\" /app/app/plugins/tgmediacenter/src/components/version.js"
   ```
   两者应与你安装的版本号一致。若这里就是旧版本，说明**插件根本没更新**（与浏览器缓存无关），
   需要在插件页重新安装/更新。
1. 硬刷新页面（`Ctrl + Shift + R`），确认后端是否已经生效（状态徽章能反映新版后端）。
2. 若前端仍为旧行为，核验落盘产物：
   ```bash
   docker exec <容器名> sh -c \
     "grep -o 'expose_Config-[A-Za-z0-9_-]*' /app/app/plugins/tgmediacenter/dist/assets/remoteEntry.js"
   ```
   输出应与仓库 `dist/assets/` 中的实际文件名一致；不一致说明更新未落盘，需重新安装插件。
3. DevTools → Network 搜 `remoteEntry.js`，确认返回内容中的 chunk 名与仓库一致。

> 宿主对插件静态文件是**每次请求从磁盘流式读取**（响应头 `no-cache, must-revalidate`，
> 无服务端缓存），所以"看到旧界面"只有两种可能：浏览器里的旧联邦组件，或插件未真正更新。

### 界面提示"前端组件 vX ≠ 后端 vY"

说明浏览器仍在用**缓存的旧联邦组件**（入口 `remoteEntry.js` 无哈希，宿主加载器也不加缓存
参数）。按 `Ctrl+Shift+R` 硬刷新即可；这也是判断"我到底在跑哪一版"最快的方式。

### 会话（频道 / 群组）只能从下拉选择

监控 / 转发 / 缓存三个面板的会话选择统一来自「TG 凭证」页的**对话列表缓存**，
**不再支持手动输入会话 ID**（v1.5.2 / v1.5.3 起移除）。看不到想要的会话时：

1. 到「TG 凭证」页点「刷新对话列表」；
2. 回到对应面板点「刷新状态」，下拉里就会出现该会话。

若该会话在刷新后仍不出现，说明**当前账号看不到它**（未加入 / 已退出 / ID 失效）——
必须先让账号可见该会话（重新加入频道或群组），否则任何形式都监听/转发不到。
已保存但不在缓存里的会话 ID 仍会兜底显示（显示为原始数字），老规则打开不会变空白。

### 遇到过 502 / "Request failed with status code 502"

这是**反向代理读超时**，不是业务失败：首次发码要现连 Telegram，经代理时"连接 + 发码"可能
超过网关的读超时（通常 60 秒），于是前端拿到 502，而后端仍在继续跑并**真的把验证码发出去了**
（所以会出现"报错但收到码"）。

现在的处理：插件载入时预连接客户端，各操作的时间预算都压到网关超时之内，界面也会把 502
翻译成可操作提示并自动回查真实状态。若仍偶发，等 10 秒重试即可。

### 对话列表拉取很慢 / 超时

`iter_dialogs` 要遍历账号全部对话（上限 800 条），经代理时可能耗时较久：

- **登录后不会自动拉取**（v1.1.7 起）：请手动点「刷新对话列表」，登录本身已经是完整成功状态；
- 后端预算"连接 10 秒 + 拉取 40 秒"、前端接口上限 58 秒，超时会给出明确原因而不是一直转圈；
- 若提示"TG 运行时已停止（可能插件被重载）"，说明拉取过程中插件被重载（例如你同时点了
  「保存配置」），点一次「刷新对话列表」重试即可；
- 拉取期间建议不要同时保存配置。

### 升级后显示"会话已保存 / 未登录"、或报 Cannot send requests while disconnected

`start()` 只保证"线程活着 + 客户端对象已创建"，**不代表网络层还连着**；代理抖动或 Telegram
主动断开后，客户端就处于"线程在跑但发不出请求"的状态。

现在的处理（无需人工干预）：

- 每次真要发请求前都会做一次连接健康检查，断开则重连并**重试一次**；
- 探活间隔压到最长 30 秒，掉线自动恢复；
- 打开配置页（或点「刷新状态」）时，只要发现"已配置凭证但未连接"，就在**后台**安排一次连接
  ——等约 10 秒后再点「刷新状态」即可看到已登录；
- 也可以点右上角**「重连」**立即重试。

> 这种情况不等于登录已失效：会话串存在插件数据里，重连后通常仍是登录态。

### 凭证必须先「保存配置」

后端连接用的是**已保存**的配置，不是表单里当前输入的值。填完 API ID / Hash / 手机号后
要先点底部的「保存配置」，再发送验证码。

### 会话（登录态）为什么放在插件数据里

宿主「保存配置」是**整份覆盖**写入，而配置表单只包含用户可编辑的字段。若把登录会话串存在
配置里，用户登录后随手点一次「保存配置」就会把它清空（表现为"已登录"突然变"未登录"）。
因此会话统一存**插件数据**（`save_data`），配置只保留用户可编辑项；旧版本遗留在配置里的
会话会在插件初始化时自动迁移并清除。

> 同理，后续任何**后端自管状态**都不要放进配置。

### 验证码发到哪里 / 为什么要等倒计时

- 验证码的**投递渠道由 Telegram 决定**，不一定是短信：若该账号已在某处登录，验证码通常直接
  发到**已登录的 Telegram 应用内**（`delivery: app`）。接口会返回 `delivery_text`，界面上也有明示。
- Telegram 对同一号码的发码有**最小间隔**（返回值里的 `timeout`，通常 60 秒）。界面上的
  「重新发送（Ns）」倒计时即来自它；**倒计时内点发送会被本地直接拦下**，因为此时请求必然失败。
- 因此：**已收到验证码就直接输入登录，不要重复点发码**。刷新页面不会丢——待登录上下文
  （`pending_login`）持久化在后端，页面加载时会自动恢复登录向导。

> 若手动调用接口重复发码，可能看到 `SEND_CODE_UNAVAILABLE`：这是 Telegram 对"重发"请求的拒绝
> （Telethon 会在客户端已缓存 `phone_code_hash` 时把请求改写成 `ResendCodeRequest`）。
> v1.1.2 起已在发码前清理该缓存并做本地冷却拦截，同时把提示翻译为中文。

## 常见问题（FAQ）

### 更新插件后界面没变化 / 仍报旧错误

优先看上方「已知行为」第一条：先确认容器内落盘文件真的到了目标版本
（`grep plugin_version` / `grep FRONTEND_VERSION`），再 `Ctrl + Shift + R` 硬刷新。
联邦入口 `remoteEntry.js` 无哈希、宿主加载器不加缓存参数，浏览器只会保留旧组件，
所以"看到旧界面"只有两种可能：插件没真更新，或浏览器在用缓存旧组件。

### 插件图标不显示 / 还是默认拼图

图标要写**完整 https URL**（见上方「开发与发版 · 图标必须写完整 URL」）。只写裸文件名时，
宿主前端会去本地 `./plugin_icon/<文件名>` 取图，多数自建部署下该路径 404，回落成内置拼图。
另外 nginx 对图片 `expires 1y; immutable`，**只换图标内容、不改 URL 基本无效**，
需要换 URL 或清缓存 / 重启进程才能刷新。

### 监控 / 回搜提示「媒体库未收录」是什么意思

识别器从 115 分享标题或 TG 消息里解析出媒体名（如 `片名 (年份) SxxExx`），
拿去宿主媒体库（Emby / 本地库）做**定向查询**却查不到对应条目。常见原因：
未刮削、改名不一致、或 TMDB ID 对不上。插件不会臆造条目，查不到就是查不到；
此时「仅缺失时推送」等依赖媒体库的判断无法工作，状态卡会显示该数据源不可用。
（媒体库查询全部是定向精确查询，代价与库规模无关，请勿引入全量兜底。）

### 115 登录态失效 / Cookie 过期

115 扫码得到的 Cookie 会过期或被踢。失效时「115 网盘」面板状态会变、转存会失败，
通知里会附重新扫码引导（同一故障 6 小时内只提醒一次）。重新扫码即可——
Cookie 存在插件内部、不占配置项，不会被「保存配置」清掉。

### 会话下拉里找不到想要的频道 / 群组

监控 / 转发 / 缓存三个面板的会话都来自「TG 凭证」页的**对话列表缓存**，不再支持手填 ID。
看不到时先到「TG 凭证」页点「刷新对话列表」，再回对应面板「刷新状态」。
刷新后仍不出现，说明当前账号本身看不到该会话（未加入 / 已退出 / ID 失效），
须先让账号可见（重新加入）才监听 / 转发得到。

## ② 115 网盘（P2）

用于把资源监控 / 通用转发命中的链接推送到 115：分享链接**转存**、磁力与 eD2k **离线下载**。

**登录方式：扫码登录（推荐）**——选择登录设备（支付宝小程序 / 微信小程序 / 115 各 App 端）
→ 点「扫码登录」→ 用 115 App 扫码并在手机上确认，插件会自动写入 Cookie 并检测连接。

> **设备列表只保留 App 端**：115 对网页 Cookie 的会话有设备风控——读取账号信息与空间配额可以通过，
> 但 **列目录 / 转存 / 离线下载**等文件类接口会返回 `请先验证安全密钥`（账号级二次验证）。
> 扫码绑定 **App 设备**（如支付宝小程序）的会话被 115 视为官方客户端，**不会触发该验证**。
> 社区工具（xiaoya-alist、alist、p115client）都采用同样的做法。
> v1.2.3 起**只保留扫码登录**：Cookie 由扫码换取后保存在插件内部（不显示、不可粘贴，也不受「保存配置」影响），失效时重新扫码即可。

需要先设置**转存文件夹 CID**（转存与离线都保存到该目录）：在 115 里打开目标文件夹，
地址栏 `cid=` 后面的数字就是；填好后点「校验目录」确认可用。

**推送测试面板**可先用「解析测试」确认链接能被正确识别（不需要 Cookie、不会提交），
再用「推送到 115」实际提交，逐条结果可见。

**通知**（P7 起）：「115 网盘」面板的「通知」卡片里可分别开关三类通知（都走 MoviePilot 通知渠道）：

- **转存成功后通知我**：监控 / 转发命中后往 115 转存（或离线）成功，按批汇总一条（如「已转存 3 条」）；
- **转存失败后通知我**：汇总失败条数与原因，115 登录态失效会附上重新扫码引导（同一故障 6 小时内只提醒一次）；
- **回搜到资源后通知我**：订阅回搜在缓存里找到缺失资源并推送后的结果汇总。

关闭哪类就收不到哪类。通用转发本身不发送通知（转发结果在「通用转发」面板的流水里看）。

实现方式（见设计文档附录 D 方案 A）：**自实现 115 Web 接口子集，零新增依赖**
（复用宿主 `AsyncRequestUtils`），不引入带 37 个传递依赖的社区库。

已知边界：

- 离线配额 115 侧经常取不到，界面会显示"获取失败"，不影响其它能力；
- 单批上限用于分批提交，单次同步调用还有 40 秒预算与 30 条上限（防止撞上网关超时），
  超额部分会提示"剩余 N 条（可再次点击继续）"。

## ⑧ 消息交互（P8）：私聊发链接直接转存

私聊 MoviePilot 机器人**直接发 115 分享链接 / 磁力 / eD2k**，插件会转存（或离线）到 115，
并回一条回执：

```
胖虎媒体中心 · 链接转存回执
新转存 1 条：
115分享:sws9cl133hx
转存成功
```
- **已转存过**会单独标注：`已转存过，本次未重复保存`（115 侧把「已转存 / 已存在 / 重复」
  也报成成功，回执里必须和新转存区分开）；
- 失败回执带 `失败原因：…`；
- 消息里**没有可推送链接时不会有任何回复**（避免随便说一句都被打扰）；
- 单条消息最多处理 5 条链接、40 秒预算，超额部分提示"还有 N 条未处理（可再发一次）"；
- 回执与其余通知一样走宿主「通知」渠道（用哪个渠道、发给谁跟宿主的「通知」设置一致）；
- 「115 网盘」面板底部开关**允许私聊机器人发链接直接转存 115** 可整体关闭（默认开启）。

实现：监听宿主 `EventType.UserMessage`（宿主在内置搜索 / 指令都不匹配时才广播该事件），
处理器定义在插件主类上（宿主事件分发只按插件实例解析，普通类方法会被静默跳过）。

## ④ TG 资源监控（P4）

监听指定频道 / 群组的**新消息**：聚合窗口（默认 3 秒，合并同频道批量消息）→ 净化（去广告行）→
宿主识别引擎 `MetaVideo` 解析标题 / 季集 → 按规则决策 → 命中入推送队列。

**规则字段**（对齐 MA 的 `resource_subscriber_rules`）：

| 字段 | 说明 |
| --- | --- |
| 监听频道 / 群组 | 多选；下拉来自「TG 凭证」页的对话列表缓存 |
| 推送目标 | `smart`（115 可用则转存，否则仅记录）/ `pan115` / `tg_forward`（转发原消息到目标会话，目标会话同样从对话缓存下拉选择）/ `none` |
| 仅缺失时推送 | 依据 MP 媒体服务器 `media_exists()` + 订阅快照 `lack_episode` 判断；两级都不可用时命中会跳过并说明原因 |
| 仅推已订阅 | 独立开关，默认开：只推订阅列表里有的资源。关掉「仅缺失时推送」后它仍然生效（否则会变成全量推送）；识别不出片名的纯链接消息照旧放行；订阅数据源不可用时放行 |
| 自定义关键词 | 任一关键词命中才继续处理（与「仅缺失」是 AND 关系） |

**缺失判断**：先用订阅快照预筛（`lack_episode=0` 直接跳过），再查媒体服务器
（电影不存在即缺；剧集按 `seasons: {季: [已存在集]}` 判断目标集）。判断结果有 60 秒 TTL 缓存。
状态卡的「缺失判断」区会显示当前可用的数据源——两项都不可用时，「仅缺失」规则无法工作。

**命中流水**：每条被处理的消息（含跳过）都会记录，可按决策过滤、按关键词搜索（片名 / 规则名 /
说明，如输入「玉簟秋」只列相关流水）、分页查看，用于复盘「为什么这条没推」。
流水会越攒越多，面板提供两个清理入口：**删除筛选结果**（只删当前决策 + 关键词筛出来的那批）与
**清空本类流水**（清空本面板的全部流水）；两者都要二次确认，且只影响本面板（监控与转发的流水互不影响）。

**规则测试**：粘贴一条频道消息原文，即可预览每条规则的处理结果（识别 / 缺失判断 / 决策），
不落库、不入队、不推送——配规则时先用它验证，不必等真实消息。

**风控纪律**（个人号）：聚合窗口 + 全局转发冷却（`tg_user_cooldown_seconds`，默认 5 秒）+
FloodWait 退避；命中入队后由内置 worker 线程按目标分派执行，失败指数退避重试（最多 3 次）。

**去重**：同规则同消息只处理一次（数据库唯一键），插件重载 / 事件重放不会重复推送。

已知边界：

- 只监听**新消息**（不处理历史消息与编辑）；历史回抓属于 P5 缓存模块；
- `tg_forward` 只做整条消息转发；关键词 / 扩展名匹配、内容转换与置顶属于 P6 转发引擎；
- 识别依赖宿主 `MetaVideo`，标题格式太偏的可能识别不出（流水里记为「无法识别」）。

## ⑤ 历史消息缓存（P5）

把指定频道 / 群组的历史消息归档到本地库，供「新增订阅回搜」使用：

- **实时入库**：关心会话的新消息直接入库（与监控共用同一条事件流水线）；
- **回溯补齐**：按增量位点或时间范围分批拉取（`cache_sync_mode`：`relative` 近 N 天 / `absolute` 指定区间 / `all` 全量），
  批次之间会 sleep 并处理 FloodWait，中断后从位点继续；
- **检索**：`/cache/search` 支持按关键词检索缓存消息；
- **订阅回搜**：宿主新增订阅时（事件触发，定时任务兜底）按标题回搜缓存 → 逐条判缺失
  （媒体库逐集比对为准）→ 过滤无链接 / 已推送 → 入推送队列 → 结果通知。

已知边界：

- 首次运行只建立订阅基线，不会把已有订阅全部回搜（避免一次性推爆）；
- 缓存频道与监控规则的监听频道互相独立，可以只缓存不监控。

### 洗版回搜（1.13.24，独立开关）

`cache_reshuffle_enabled`（默认关）改变的是**定时兜底 / 手动兜底**的口径，不影响
`subscribe.added` 的实时通道：

| | 关（默认，与 1.13.23 一致） | 开 |
|---|---|---|
| 范围 | 只处理快照 diff 出的**新增**订阅 | 每轮遍历**全部**订阅 |
| 判定 | 逐条 `is_missing`（媒体库逐集比对） | **跳过媒体库判定**，只要求消息有可用链接 |
| 去重 | 按 `cache_search` 虚拟规则的命中流水 | 按**任意路径**的命中流水（监控 / 补扫 / 回搜推过都算） |
| 节奏（1.13.25） | 无（新增订阅数量天然有限） | 入队**不限条数**，推送由 worker 按「每批条数 / 批间隔」匀速消费 |
| 通知标题 | 「胖虎媒体中心 缓存回搜」 | 「胖虎媒体中心 洗版回搜」 |

用途：订阅早已存在，但频道后来才放出更高质量的资源（4K / 原盘 / 更好的压制），
常规兜底因为「订阅不是新增」永远不会再捞它。开启后每轮都把这些老订阅重新过一遍缓存，
只要这条消息没被任何路径推送过就入队，等于自动洗版。

注意：

- 快照在洗版模式下照旧维护，所以随时关掉开关都能回到常规口径；
- 1.13.25 起不再限制单轮入队条数：一轮定时把全部订阅的匹配都灌进推送队列，
  再由推送 worker 分批下发（`cache_push_batch_size` 每批条数 1~200，默认 10；
  `cache_push_batch_interval` 批间隔 5~3600 秒，默认 15）。这样一次定时就能推完全部，
  不需要反复手点「立即洗版回搜」；实时监控 / 普通转发任务与洗版批量任务**各占一半额度**，
  不会被洗版洪峰挤掉；
- 回搜通知**只报真正推出去的资源**：一条都没推（「已推送过」「订阅无缺集」
  「无可用链接」「未订阅」）时完全不发通知，这些判定照旧写命中流水，运行详情页可查；
- 媒体库判定被完全跳过，因此**库里已有的资源也会被再推一次**——这正是洗版的语义，
  但如果只想补缺口，请保持开关关闭。

#### 洗版规则：七维字典序（1.13.32）

1.13.31 的加权总分（分辨率 40 · 片源 25 · 编码 15 · 特效 15 · 音轨 5）是拍脑袋定的序数，
两个副作用很实在：4K WEB-DL 这种「分辨率高但片源差」的会靠权重压过 1080p REMUX；
而到底谁该赢完全由那几个魔数隐式决定，改一次权重结论就翻盘。1.13.32 换成**维度优先级
（字典序）**，配置项合并为一个 `cache_wash_rules`：

- **七个维度**：质量（原「片源」）→ 分辨率 → 色彩模式 → 音频规格 → 视频编码 → 扩展名 → 文件体积；
- **质量锁第 1 维**（不可拖）：片源是决定观感的第一因素，`REMUX > BluRay > WEB-DL > WEBRip > HDTV > CAM/TS`；
  所以 1080p REMUX 永远赢 2160p WEB-DL，且不依赖任何权重数字；
- **其余六维可拖拽排序**（行序即优先级）：每轮比较先比质量，打平才看下一维；
- **每维是一排 chip，chip 左右位置即维度内优劣**，左→右由优到劣；「✓/✕」只决定该值是否保留，
  与位置无关（✕ 的 chip 仍停在真实档位上，便于对照）；
- **未列出的值**默认排除，可按维切成「垫底纳入 / 置顶纳入」；**解析不出的值不参与该维比较**，
  交给 TopN 兜底（否则标题不带分辨率的频道会被全卡死）；
- **文件体积**：默认「由大到小」，可设「小于 N MB」「大于 N GB」硬闸；与基线比较时按
  `size_tolerance_pct`（默认 ±5%）判「同体积」；
- **比对来源**三选（默认全开）：已推送基线 / 媒体库已存在 / 下载历史（PT）。任一处有
  「同质量 + 同分辨率 + 同体积（±容差）」就判持平不推——这条专门修 1.13.31 的漏推：
  PT 已经下过同质量同大小的资源，插件因为基线只记「自己推过的」而照推；
- **同集每轮最多推几条**（`top_n`，默认 1，0 = 不限）保留为兜底：解析不出画质的候选不参与比较，
  靠它收敛；
- 判定顺序：准入过滤（✕ 值 / 未列出值 / 体积越界）→ TopN 择优 → 与基线逐维比较；
- 想回到 1.13.24 的「命中即推」：关掉「洗版回搜」总开关即可；只想放宽收口，把 `top_n` 填 0、
  并把各维 ✕ 全部点亮。

配置在「消息缓存 → 洗版规则」子页；JSON 形如：

```json
{
  "order": ["quality", "resolution", "effect", "audio", "codec", "ext", "size"],
  "values": {
    "quality": [{"v": "remux", "on": true}, {"v": "bluray", "on": true}],
    "resolution": [{"v": "2160p", "on": true}, {"v": "1080p", "on": true}]
  },
  "unlisted": {"quality": "deny", "ext": "deny"},
  "size": {"min_mb": 0, "max_gb": 115, "prefer": "desc"},
  "top_n": 1,
  "size_tolerance_pct": 5,
  "compare_sources": ["pushed", "library", "history"]
}
```

### 跳过宿主的「新增订阅首次全站搜索」（1.13.8，独立开关）

宿主保存订阅后会把这条订阅排进一次全站搜索（`source=new`，约 60 秒后自动开始）。
本插件的订阅回搜已经从 TG 频道缓存里找同一部作品，两边都跑等于重复抓取。

配置页 **「重复获取治理」→「新增订阅首搜（反向闸门 R1）」** 是**独立开关**
`skip_first_search_enabled`（默认关，与「订阅回搜」开关互不依赖）。打开后：

- 插件在**宿主入队之前**把新订阅直接置为「订阅中」（`state` N→R），
  这次全站搜索不再发生，订阅活动里也不会出现「已安排搜索」记录；
- 后续仍按宿主正常的订阅搜索间隔继续搜（订阅自己的间隔 / 默认 24 小时），
  不是永久屏蔽；
- 实现方式：包住宿主入队方法 `_SubscribeChain__queue_new_subscription_search`
  （含异步版）；插件停用 / 重载时还原，宿主升级后方法名漂移则整体失效并留 WARNING，
  不影响宿主原有行为。

> 为什么不能靠监听 `SubscribeAdded` 事件（1.13.5~1.13.7 三版失败的原因）：
> 宿主广播是**异步**的（`send_event` 只入队，后台消费线程稍后分发），而
> `notify.py` 在 `send_event` 之后**同步**入队首搜；等处理器跑起来任务已经入队。
> 而且已入队的任务在执行时只认 `state='S'`（暂停）才跳过，写 `R` 也拦不住。

## ⑥ TG 通用转发（P6）

监听来源频道，按规则命中后把消息转发到目标会话：

- **匹配**：逻辑一 = 自定义关键词（可多关键词，任一命中；不启用 = 该级不设限）；
  逻辑二 = 文件扩展名（如 `mkv` / `[mp4]`）。**两级之间恒为 AND**，都启用时必须同时满足；
  转发**不要求识别成功**，也不依赖订阅（纯转发功能）；
- **内容转换**：每行 `原文 -> 替换文`，左侧按正则编译、逐条顺序应用；
  转换后以**新消息**发送（不改动原消息）；
- **置顶**：开启后转发完把消息置顶（`pin_link_keywords` 可限定只置顶命中关键词的链接）；
  置顶失败不影响转发成功判定；
- **流水与统计**：转发决策落同一张流水表的 `forward` 分栏，与监控互不干扰。

**风控纪律**：转发与监控共用同一把**全局冷却门**（`tg_user_cooldown_seconds`）与 FloodWait 退避；
规则 ID 用 `f` 前缀（监控规则是 `r`），去重键天然不冲突。

## 运行详情与仪表盘（P7）

- **详情页**（插件卡片「详情」）：TG / 115 / 缓存三张状态卡 + 流水线统计（监控命中 / 转发命中 / 队列）
  + 最近流水（监控最近 10 条，来源列显示频道名）+ 快捷操作（连接 TG、刷新对话列表、检测 115、同步缓存、检查新增订阅）；
- **仪表盘卡片**（宿主首页）：TG / 115 / 缓存状态徽章、命中与失败计数、最近流水
  （默认摘要 5 条，点「加载更多」每次追加 20 条、最多 100 条；完整流水与关键词搜索在「资源监控」面板）；
- 两者都只调 `/overview`（一次请求拿齐各模块状态），且**单模块异常不影响整页**；
  详情页 30 秒自动刷新，操作按钮执行后立即刷新。

## 限流与退避（P7 收口）

- **一份退避状态**：冷却门是插件级单例，转发 / 置顶（写）与刷新对话 / 历史回溯 / 会话反查（读）
  共享同一份 FloodWait 截止时刻——FloodWait 是**账号级**限制，读撞上之后写同样会被拒；
- **上报点**：TG 调用包装层（凭证模块）、对话缓存预热、缓存回溯、会话反查，撞 FloodWait 都会写回冷却门；
- **重试**：推送失败按 30s → 60s → 120s…（上限 600s）指数退避，最多 3 次，用尽标记 `failed`；
- **可观测**：状态卡与详情页都会显示当前是否处于 FloodWait 退避中及剩余秒数。

## 开发与发版

### 版本号六处同步

每次发版，下面六处必须同时改为同一版本号，否则 CI 门禁会失败、单测也会爆：

1. `__init__.py` 的 `plugin_version`；
2. `package.json` 的 `version`；
3. `package.v3.json` 的 `version` 字段；
4. `package.v3.json` 的 `history` 最新键（如 `"v1.13.24": "..."`）；
5. `src/components/version.js` 的 `FRONTEND_VERSION`；
6. `tests/v3/tgmediacenter/test_plugin.py` 里的版本断言。

门禁脚本 `check_plugin_versions.py` 会校验版本一致性与 `history` 键存在；单测
（`tests/v3/tgmediacenter/test_plugin.py`、`test_p7_polish.py`）也会断言这几处相等。

### 前端改动必须重建 dist

前端是 Vue 联邦远程组件，`vite` 配置 `emptyOutDir: false`，所以 `pnpm build`
**先执行 clean 清理 `dist/assets` 旧产物**再产出新联邦产物。不清理会堆积带旧哈希的
产物，最终被打进发布包、前端永不更新。

```bash
pnpm install
pnpm dev      # vite build --watch，配合宿主 PLUGIN_LOCAL_REPO_PATHS + PLUGIN_AUTO_RELOAD 联调
pnpm build    # 先 clean 再产出联邦产物
```

构建后必须通过联邦 CSS 门禁（作用域样式泄露校验）：

```bash
python ../../../.github/scripts/check_federation_css.py
```

### 跑单测

```bash
# 用宿主 venv 的解释器（裸 python 缺 sqlalchemy，连 conftest 都加载不了）
D:\projects\MoviePilot\.venv\Scripts\python.exe -m pytest tests\v3\tgmediacenter -q
```

本插件的 `telethon` / `python-socks` / `apscheduler` 都是**可选依赖**（缺了降级、插件照样加载），
所以历史上同一份用例的结果取决于"跑测试的机器装没装包"。`tests/v3/tgmediacenter/conftest.py` 现在统一处理了这点：

- **纯调度类型**（`CronTrigger`）缺包时补一个最小桩，让 `get_service()` 的注册逻辑在任何环境都被真正覆盖；
- **telethon** 不全局打桩，而是由用例声明 `telethon_available` fixture（它同时修正 `runtime.TELETHON_AVAILABLE`），
  涉及凭证就绪、`_register_handler` 注册形状的断言因此不再随机器变化。

结果是：裸 venv（无 telethon / apscheduler）、装了依赖的 venv、宿主 venv 三种环境结果一致（1.13.32 在宿主 venv 实测 **575 passed**）。
在宿主 venv（`D:\projects\MoviePilot\.venv`，另两个插件的依赖也齐）里还可以直接
`python -m pytest tests\v3` 一次跑完三个插件——本目录有 `__init__.py`
（另两个插件没有），用来消除与 `tests/v3/embycovercenter/test_plugin.py` 的同名冲突。

注意 CI **不跑 pytest**（`release.yml` 只有版本门禁与联邦 CSS 门禁），测试全靠本地/发版前自觉执行。

### 发布流程与 CI 行为

`.github/workflows/release.yml`（"Plugin Release"）在 **push 到 `main` 且改动
`package.v3.json`**（或 `package.json` / `package.v2.json`）时触发，也可手动
`workflow_dispatch`。流程：

1. 先跑两个门禁：`check_plugin_versions.py` + `check_federation_css.py`；
2. 只处理各 package 文件里 `release == true` 的条目，按其 `version` 打包
   `tgmediacenter_v<版本>.zip`（zip 的是插件目录，排除 `__pycache__`）；
3. 建 / 更新 tag `<插件ID>_v<版本>`（如 `TgMediaCenter_v1.8.2`）与同名 Release，
   发布说明取自 `history["v<版本>"]`。

- **触发条件是 `package*.json` 有改动**：只推源码 / README 而不动 `package.v3.json` 时
  **不会出包**——发版必须改版本号（或手动 dispatch）。
- **同版本重跑会替换**：Release 已存在时先删旧 Release 与 tag 再重建（幂等，可安全重发）。
- **插件目录自上次 tag 起无改动则跳过打包**，只更新发布说明。
- 图标两份都要更新：索引仓库 `icons/tgmediacenter.png`（列表用）+ 插件目录内
  `plugins.v3/tgmediacenter/tgmediacenter.png`（随包发布）。

### 图标必须写完整 URL

`package.v3.json` 的 `icon` 与 `__init__.py` 的 `plugin_icon` **都写完整 https URL**
（`https://raw.githubusercontent.com/strongrexue/MoviePilot-Plugins/main/icons/tgmediacenter.png`）。

根因：宿主前端 `PluginCard.vue` 加载图标时，若值不是 http 开头则请求本地
`./plugin_icon/<文件名>`，该路径在多数自建部署下 404；只有完整 URL 走图片代理才稳定。
且 nginx 对图片给 `expires 1y; immutable`，**换图不换 URL 基本无效**——
改图标内容后若要立即生效，应当换一个 URL（或让用户清缓存 / 重启进程）。

### 前端更新后必须硬刷新

联邦入口固定叫 `remoteEntry.js`（无哈希），宿主加载器也不追加缓存参数，SPA 只在
**页面加载时**拉取一次远程组件。因此更新带前端改动的版本后，必须整页硬刷新
（`Ctrl + Shift + R`），否则浏览器仍在使用旧组件代码。详见上方「已知行为」。
